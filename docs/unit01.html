Unit 01 · OS Fundamentals

Thread vs Process

Thread, ProcessInfo, DispatchQueue

OS가 프로그램을 실행하는 두 가지 단위 — Process와 Thread의 차이, Context Switching 비용, 그리고 Race Condition이 발생하는 원리를 iOS 런타임 관점에서 이해합니다.

Core Concepts

핵심 개념 정리

Process (프로세스)
  • OS가 프로그램을 실행하는 독립 단위
  • 고유한 메모리 공간: Code / Data / Heap / Stack 영역 보유
  • iOS에서 앱 하나 = 프로세스 하나 (App Sandbox)
  • 프로세스 간 통신은 IPC(Inter-Process Communication) 필요
Thread (스레드)
  • 프로세스 내에서 실행되는 경량 실행 단위
  • Code · Data · Heap 공유, Stack만 개별 소유
  • 생성 비용: Thread << Process
  • iOS: 메인 스레드(UI) + 백그라운드 스레드 구조
Context Switching
  • OS 스케줄러가 실행 단위를 교체하는 과정
  • Thread 전환 비용 << Process 전환 비용
  • 메모리 공간 교체가 불필요하기 때문
  • 너무 많은 스레드 → 오히려 Switching 오버헤드 증가
Race Condition
  • 두 스레드가 공유 자원에 동시 접근 시 발생
  • 결과가 실행 순서에 따라 달라지는 버그
  • 비결정적(non-deterministic) — 재현이 어려움
  • 예방: Serial Queue, Lock, Actor 등
구분ProcessThread
메모리 공간독립 (Code/Data/Heap/Stack 모두)Stack만 독립, 나머지 공유
생성 비용높음낮음
통신 방법IPC (소켓, 파이프 등)공유 메모리 직접 접근
iOS에서앱 1개 = 프로세스 1개여러 스레드 동시 실행
격리강함 (크래시가 다른 프로세스 영향 없음)약함 (한 스레드 크래시 → 앱 전체 영향)

Memory Model

Value Type vs Reference Type

struct는 Stack에, class는 Heap에 저장됩니다. Stack 접근은 스레드 독립적이므로 안전하지만, Heap의 class 인스턴스를 여러 스레드가 공유할 때 Race Condition이 발생합니다.
Stack vs Heap 메모리 영역 체감
// ✅ Value Type — Stack에 저장 (복사)
struct PointValue {
    var x: Int
    var y: Int
}

var p1 = PointValue(x: 0, y: 0)
var p2 = p1      // 복사 — p1과 독립
p2.x = 99
print(p1.x)     // → 0  (영향 없음)
print(p2.x)     // → 99

// ❌ Reference Type — Heap에 저장 (참조 공유)
class PointRef {
    var x: Int
    var y: Int
    init(x: Int, y: Int) { self.x = x; self.y = y }
}

let r1 = PointRef(x: 0, y: 0)
let r2 = r1      // 참조 복사 — 같은 객체
r2.x = 99
print(r1.x)     // → 99  (r1도 바뀜!)
print(r2.x)     // → 99

Race Condition

안전하지 않은 카운터 vs Thread-safe 카운터

❌ UnsafeCounter — Race Condition 발생 가능
class UnsafeCounter {
    var count = 0

    func increment() {
        // 이 3단계 사이에 다른 스레드가 끼어들 수 있음
        // 1. count 읽기
        // 2. +1 계산
        // 3. count 쓰기
        count += 1
    }
}

let counter = UnsafeCounter()
let group = DispatchGroup()

for _ in 0..<1000 {
    DispatchQueue.global().async(group: group) {
        counter.increment()
    }
}
group.wait()
print(counter.count)  // → 1000이 아닐 수 있음!
✅ SafeCounter — Serial Queue로 보호
class SafeCounter {
    private var count = 0
    private let queue = DispatchQueue(label: "com.leeo.safeCounter")

    func increment() {
        queue.sync {
            count += 1   // 직렬 큐가 한 번에 하나만 실행 보장
        }
    }

    var value: Int {
        queue.sync { count }
    }
}

let safe = SafeCounter()
for _ in 0..<1000 {
    DispatchQueue.global().async(group: group) {
        safe.increment()
    }
}
group.wait()
print(safe.value)   // → 항상 1000 ✅

Thread Info

스레드 & 프로세스 정보 확인

Thread / ProcessInfo API
import Foundation

print(Thread.current)                              // 현재 스레드
print(Thread.isMainThread)                         // 메인 스레드 여부
print(ProcessInfo.processInfo.processIdentifier)   // PID
print(ProcessInfo.processInfo.processorCount)      // 물리 코어 수
print(ProcessInfo.processInfo.activeProcessorCount) // 활성 코어 수

// 백그라운드 → 메인 전환 패턴
DispatchQueue.global(qos: .userInitiated).async {
    print("백그라운드 | isMain: \(Thread.isMainThread)")

    DispatchQueue.main.async {
        print("메인 복귀 | isMain: \(Thread.isMainThread)")
    }
}

Practice

실습 체크리스트

  • UnsafeCounter 결과가 1000이 아닌 경우를 여러 번 실행하여 확인
  • SafeCounter의 queue를 concurrent로 바꾸면 어떻게 되는지 실험
  • Value Type과 Reference Type이 스레드 안전성에 미치는 차이를 설명

Interview

면접 질문 연습

iOS에서 Thread와 Process의 차이는?
Process는 독립된 메모리 공간(Code/Data/Heap/Stack 모두)을 가진 실행 단위입니다. Thread는 프로세스 안에서 Stack만 독립적으로 갖고 나머지를 공유하는 경량 실행 단위입니다. iOS에서 앱 하나는 프로세스 하나이며, 그 안에서 메인 스레드(UI)와 여러 백그라운드 스레드가 동작합니다.
메인 스레드가 UI 전용인 이유는?
UIKit/AppKit은 thread-safe하게 설계되지 않았습니다. 여러 스레드에서 동시에 UI 컴포넌트에 접근하면 레이아웃 상태가 불일치하거나 크래시가 발생할 수 있습니다. Apple은 이를 단순화하기 위해 "모든 UI 업데이트는 메인 스레드에서"라는 규칙을 강제합니다.
Race Condition이란 무엇이고 어떻게 예방하는가?
두 스레드가 공유 자원에 동시에 접근하고 그 중 하나 이상이 쓰기를 할 때, 실행 순서에 따라 결과가 달라지는 버그입니다. 예방책으로는 ① Serial DispatchQueue, ② NSLock/mutex, ③ Swift의 actor (컴파일러 강제), ④ Atomic 연산이 있습니다.
