Data Race란?

두 스레드가 동시에 같은 메모리 위치에 접근하고, 그 중 하나 이상이 쓰기 작업일 때 발생하는 미정의 동작(Undefined Behavior)입니다.

  • 비결정적(non-deterministic) — 실행할 때마다 결과가 다를 수 있음
  • 재현이 어려워 디버깅이 까다로움 — "하이젠버그"
  • Xcode Thread Sanitizer(TSan)로 런타임 탐지 가능
  • Swift 6부터 컴파일 타임에 Sendable/Actor로 정적 방지
// Data Race 발생 예제
// ❌ Thread-safe하지 않은 카운터
class UnsafeCounter {
    var count = 0
    func increment() {
        count += 1 // 읽기→계산→쓰기 사이에
                  // 다른 스레드 개입 가능!
    }
}

// ✅ Actor로 해결
actor SafeCounter {
    var count = 0
    func increment() {
        count += 1 // 컴파일러가 직렬화 보장
    }
}

let counter = SafeCounter()
await counter.increment() // await 필수

Actor 격리(Isolation) 모델

Actor는 내부 상태에 대한 모든 접근을 하나의 직렬 실행 흐름으로 제한합니다. 이를 '격리(Isolation)'라고 합니다.

  • Actor 내부: 동기 접근 가능 (이미 격리 컨텍스트)
  • Actor 외부: 반드시 await — 다른 컨텍스트에서 접근
  • nonisolated: 저장 프로퍼티 접근 없는 메서드에만 사용
  • Reentrancy: await 중단 동안 다른 메서드가 실행될 수 있음
// Actor 격리 모델
actor BankAccount {
    private(set) var balance: Double

    func deposit(_ amount: Double) {
        balance += amount // 내부: 동기 OK
    }

    nonisolated var description: String {
        "BankAccount" // 상태 접근 없음
    }
}

let account = BankAccount(balance: 1000)

// 외부: await 필수
await account.deposit(500)
let bal = await account.balance

// nonisolated: await 불필요
let desc = account.description

async/await 동작 원리

await는 스레드를 블로킹(blocking)하지 않습니다. 대신 현재 실행 흐름을 '일시 중단(suspend)'하고, 스레드를 해제하여 다른 작업이 실행될 수 있도록 합니다.

  • await 지점에서 코루틴이 일시 중단됨
  • 해제된 스레드는 다른 작업을 수행
  • 결과가 준비되면 같은 or 다른 스레드에서 재개
  • 순차처럼 읽히지만 내부는 비동기적으로 동작
// 순차 vs 병렬 성능 비교
// ❌ 순차: 총 0.3초 (0.1+0.1+0.1)
let a = await fetchA() // 0.1s 대기
let b = await fetchB() // 0.1s 대기
let c = await fetchC() // 0.1s 대기

// ✅ async let: 총 ≈0.1초 (max)
async let a = fetchA() // 즉시 시작
async let b = fetchB() // 즉시 시작
async let c = fetchC() // 즉시 시작
let result = await (a, b, c)

Reader-Writer Lock 패턴

Concurrent Queue + Barrier를 조합하면 읽기는 동시에, 쓰기는 단독으로 실행하는 Reader-Writer Lock 패턴을 구현할 수 있습니다.

  • 읽기 (sync): 여러 스레드 동시 실행 → 성능 최대화
  • 쓰기 (async + .barrier): 이전 작업 완료 후 단독 실행
  • 쓰기 완료 후 읽기 작업 재개
  • OS 뮤텍스 없이 GCD만으로 구현 가능
// Thread-safe Cache
class ThreadSafeCache<K: Hashable, V> {
    private var store: [K: V] = [:]
    private let queue = DispatchQueue(
        label: "cache",
        attributes: .concurrent
    )

    func read(key: K) -> V? {
        // 동시 읽기 허용
        queue.sync { store[key] }
    }

    func write(key: K, value: V) {
        // 단독 쓰기 (barrier)
        queue.async(flags: .barrier) {
            self.store[key] = value
        }
    }
}

Combine 파이프라인 구조

Combine은 Publisher → Operator → Subscriber의 단방향 데이터 파이프라인입니다. 에러 처리와 스케줄러 전환이 파이프라인 중간에 선언적으로 배치됩니다.

  • subscribe(on:): 업스트림(생산) 스케줄러 — 네트워크·파일 I/O
  • receive(on:): 다운스트림(수신) 스케줄러 — UI 업데이트
  • AnyCancellable 미저장 → 즉시 구독 취소 (흔한 버그)
  • [weak self]: sink 클로저 내 retain cycle 방지
// 실전 네트워크 파이프라인
URLSession.shared
    .dataTaskPublisher(for: url)
    .map(\.data)
    .decode(type: User.self,
            decoder: JSONDecoder())
    .retry(2)
    .catch { _ in
        Just(User.placeholder)
    }
    .receive(on: DispatchQueue.main)
    .sink(
        receiveCompletion: { _ in },
        receiveValue: { [weak self] user in
            self?.viewModel.user = user
        }
    )
    .store(in: &cancellables)

클릭하면 핵심 답변 포인트가 펼쳐집니다.

Thread와 Process의 차이를 iOS 관점에서 설명하세요.
Process는 고유한 메모리 공간(Code/Data/Heap/Stack)을 가지는 독립 실행 단위입니다. iOS에서 앱 하나가 하나의 Process입니다. Thread는 Process 내의 경량 실행 단위로, 같은 Heap·Data를 공유하며 Stack만 개별적으로 가집니다. Thread 간 전환(Context Switching) 비용이 Process 전환보다 훨씬 작은 이유도 메모리 공간 교체가 필요 없기 때문입니다. iOS의 메인 스레드는 UIKit/SwiftUI 렌더링과 이벤트 처리를 담당하는 특수한 Thread입니다.
await는 스레드를 블로킹하나요? 동작 원리를 설명하세요.
아니요. await는 스레드를 블로킹(blocking)하지 않습니다. 대신 현재 실행 흐름(코루틴)을 '일시 중단(suspend)'하고 스레드를 해제합니다. 해제된 스레드는 다른 작업을 수행할 수 있으며, 기다리던 결과가 준비되면 같은 또는 다른 스레드에서 재개(resume)됩니다. 이것이 Thread.sleep(blocking)과 Task.sleep(non-blocking)의 근본적인 차이입니다.
Actor와 Serial DispatchQueue의 가장 큰 차이는 무엇인가요?
가장 큰 차이는 '컴파일러 강제 여부'입니다. Actor는 컴파일러가 외부 접근 시 await 없이는 컴파일 자체를 거부합니다. 개발자가 실수로 await를 빠뜨리면 컴파일 에러가 납니다. 반면 Serial DispatchQueue는 런타임 보호만 제공하며, 개발자가 올바른 큐로 작업을 제출하는 것을 잊어도 컴파일러는 알려주지 않습니다. 또한 Actor는 Sendable과 통합되어 Swift 6의 타입 시스템과 연동됩니다.
Actor Reentrancy란 무엇이고 어떻게 방어하나요?
Actor는 await 일시 중단 지점에서 다른 메서드가 같은 Actor에서 실행될 수 있습니다. 이를 Reentrancy(재진입)라고 합니다. 예를 들어 캐시 확인 후 네트워크 요청(await)하는 사이에 다른 호출이 같은 캐시 키로 들어오면 중복 요청이 발생합니다. 방어 방법: await 전에 "이미 요청 중"임을 나타내는 플래그(inFlight Set 등)를 확인하거나, await 이후에 상태를 다시 검증하는 방어 코드를 추가합니다.
AnyCancellable을 저장하지 않으면 어떻게 되나요?
AnyCancellable은 Combine 구독의 생명주기를 관리하는 토큰 객체입니다. 이 객체가 메모리에서 해제되는 순간 구독이 자동으로 취소됩니다. store(in: &cancellables)로 Set에 저장하지 않으면 해당 줄 실행 직후 임시 변수가 해제되어 즉시 구독이 취소됩니다. 결과적으로 send()나 Publisher가 값을 방출해도 sink가 전혀 반응하지 않는 것처럼 보입니다. 이것은 Combine을 처음 쓸 때 가장 많이 하는 실수 중 하나입니다.
subscribe(on:)과 receive(on:)의 차이는?
subscribe(on:)은 업스트림(Publisher → 데이터 생산) 쪽이 실행되는 스케줄러를 지정합니다. 네트워크 요청이나 파일 I/O처럼 데이터를 생산하는 작업을 백그라운드 큐에서 실행하고 싶을 때 사용합니다. receive(on:)은 다운스트림(Operator → Subscriber → UI 업데이트)이 실행되는 스케줄러를 지정합니다. sink나 assign에서 UI를 업데이트하려면 .receive(on: RunLoop.main)으로 메인 스레드를 보장해야 합니다.
